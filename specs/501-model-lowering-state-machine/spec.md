# Feature Specification: Deterministic Model Lowering and StateMachine Model

**Feature Branch**: `501-model-lowering-state-machine`

**Created**: 2026-10-12

**Status**: Draft

**Input**: User description: "Introduce the first common infrastructure for Behavior Models
(deterministic lowering, model identity, provenance, source maps, composition and ownership) and
implement StateMachine as the first model on it, so that a later RequestFlow model can build on
StateMachine without Core changes. No changes to behavior-ir-core may be made while Core work is
in progress; if one turns out to be needed, stop and report it so the right Core feature branch
can be chosen."

## Context

A **Behavior Model** is a higher-level, deterministic authoring abstraction that lowers
completely to ordinary Behavior IR. Core admits and executes the lowered module exactly as if it
had been written by hand and never learns that a model existed.

```text
StateMachine   (this feature)
RequestFlow    (future)
Approval       (future)
Domain models  (future)
      │
      ▼
Model lowering (build time only)
      │
      ▼
ordinary Behavior IR
      │
      ▼
behavior-ir-core (unchanged)
```

Governing principles, used as review tests for this feature:

- One semantic kernel, many authoring models.
- Models explain intent; Core executes meaning: `Meaning(M) := Meaning_Core(Lower(M))`.
- A model may restrict, compose and generate Core semantics; it may not hide or add runtime
  semantics.
- Lowering erases the model as a runtime requirement.
- Model source order is not semantic unless the model explicitly promises ordering.
- A model that claims control over state evolution must control every ordinary write that could
  bypass that evolution.
- No intermediate semantic layer is introduced until several models show a real shared concept.
- Core changes require semantic necessity, not model convenience.

The decisive boundary test for every construct: *would a conforming Core implementation need to
understand this construct to execute the lowered behavior correctly?* For StateMachine the
answer MUST be no.

This feature supersedes the worked example in `models/examples/state_machine/` (feature 011,
US5), which shows a single-transition lowering without identity, ownership, composition or
source maps.

## Clarifications

### Session 2026-10-12

- Q: Where should the single authoritative StateMachine lowerer live: in Rust, as a new crate
  the Python binding calls, or in Python over the existing `behavior` API? → A: Rust. One
  binding-neutral model crate in this repository owns the authoritative model representation,
  resolution, normalization, semantic validation, canonical model encoding, ModelHash,
  composition and ownership rules, StateMachine lowering and source-map production. It depends
  only on the public `behavior-engine`. Bindings (Python first, through `behavior-py`) only
  construct authoring input and source metadata. Any early checks they make are for ergonomics
  and are not authoritative. A gap in the public engine is a planning stop to classify, never a
  reason to make Python authoritative.
- Q: Should a StateMachine generate its own creation action, or should creation always be
  ordinary behavior that the build only checks? → A: Creation is never part of the
  StateMachine. The machine governs how the owned field changes on an *existing* subject
  entity. It does not own entity lifecycle and does not generate creation (or removal)
  transitions, so there is no implicit "nonexistent" pseudo-state. `entry_states` is a
  composition rule over every creation of the subject type in the composed module, whether
  hand-written or generated by another model (for example a future RequestFlow). A machine is a
  composable model and does not need to be self-sufficient. If several future models need
  reusable creation authoring, that becomes separate model infrastructure, not part of
  StateMachine.
- Q: Must a StateMachine's states be exactly all cases of the field's enum, or may the machine
  use only some of them? → A: States are implied and not declared. The state domain is derived
  from the enum type (`WType::Enum`) `T_f` of the owned field `f`: `Q := Cases(T_f)`. A machine is
  `SM = (E, f, Q_entry, 𝒯)` with `Q_entry ⊆ Q`, and each transition has `F_t ⊆ Q` and
  `q_t ∈ Q`. The enum answers "which values can this field hold"; the machine answers "which
  changes between them are permitted". The state domain and the transition relation are
  different objects. Declaring `Q` a second time would create two representations of one fact
  plus a consistency obligation that carries no domain meaning. Deriving it makes equality true
  by construction, rules out dead enum cases on an owned field, and lets ModelHash commit to the
  field's type identity instead of a copy of its cases. Machines on different fields may share
  one enum (`Q_A = Q_B`) with different transition relations (`𝒯_A ≠ 𝒯_B`), because ownership
  applies to the field, not to the enum. v1 has no subset semantics: a field that needs a
  narrower domain should use a narrower enum. Principle: a semantic fact has one authoritative
  representation whenever another can be derived exactly from it.
- Q: What should a generated transition action be called: just the transition id, or a name
  qualified with the machine id? → A: Always qualified. Transition ids are local to their
  machine; a transition's identity is `(machine semantic id, transition semantic id)`. Generated
  action names live in the module-wide Core capability namespace, so lowering MUST map that
  pair to the action name with a deterministic, injective encoding (for example
  `purchase_request__approve`). Using the bare transition id would throw away the machine
  component and turn independent models into composition conflicts that the lowering itself
  created. The encoding uses the machine's semantic id, never its display name. Renaming the
  semantic id intentionally changes capabilities and BehaviorHash, while display names can
  change freely. There is no author-chosen prefix, because the machine id already is the
  namespace. Planning MUST confirm Core's action-name grammar. Plain concatenation is acceptable
  only if the id grammar and a reserved separator make it injective; otherwise escaping or
  another canonical encoding is required. Tooling may show shorter labels through source maps
  and display metadata.
- Q: In what form should a transition's guards, extra effects, postconditions and command
  emissions reach the Rust model crate? → A: As typed ordinary Core semantic fragments, not as
  binding objects, lambdas, raw Wire JSON or a model-specific expression language. In
  `t = (F_t, q_t, G_t, E_t, P_t, K_t)` only `(F_t, q_t)` is StateMachine semantics.
  `G_t, P_t ∈ Predicate_Core*`, `E_t ∈ Effect_Core*` and `K_t ∈ CommandIntent_Core*` come
  directly from Core's domains. The model adds structure around Core semantics; it does not
  translate one expression semantics into another. Free variables in the fragments refer to
  declared semantic parameter identities (subject, inputs, context), never to binding-side
  names or lambda identity. Validation has two layers, and Core validity is necessary but not
  sufficient. The first layer is Core validity in the declared environment. The second is
  StateMachine admissibility: for example, no write to the owned field, and references only to
  declared bindings. A fragment's ModelHash contribution is its canonical Core semantic identity
  under the pinned Core version, so two authoring syntaxes that produce the same Core semantics
  hash identically. If the public `behavior-engine` lacks a typed construction or
  canonicalization operation for fragments, that is an API exposure gap under FR-035. It is
  never a reason for a model expression language.
- Q: When a change to the model crate makes an unchanged model lower to different Behavior IR,
  must the build fail until a version is deliberately bumped? → A: Yes, enforced by machine,
  and stronger than snapshot updating. For model kind `K`, model semantic version `s`, lowerer
  version `l` and Core Release `c`, lowering `L_{K,s,l,c}` is a versioned function, and
  `(K, s, l, c, ModelHash) → BehaviorHash` is immutable. Bump `s` when the meaning or admitted
  structure of the model language changes. Bump `l` when the same model contract intentionally
  lowers to different Core IR. If neither changes, BehaviorHash MUST NOT change. Collapsing
  everything into `s` would wrongly make every lowering change a language change. The exact Core
  Release identity is bound explicitly, because Core's canonical identity participates in
  BehaviorHash. Golden fixtures are executable compatibility contracts, organized under a
  versioned manifest. The gates MUST fail when an established version tuple maps to a different
  BehaviorHash, even if the fixture's expected value was edited to match. Updating a fixture
  alone is never sufficient. Principle: version identifiers identify semantic functions, not
  source-code releases.
- Q: Should Python dict insertion order decide the order of a transition's input and context
  parameters? → A: No. Parameters are canonicalized by stable semantic parameter identity:
  `I_t : ParameterId → Type` is a finite mapping, not a sequence. Reordering the declarations
  leaves ModelHash, the lowered IR and BehaviorHash unchanged. In v1 the parameter name is the
  semantic identity, so the canonical order is code-point order of names. Core invocation
  passes bindings, input and context by name (`RequestedInvocation`), so parameter order is not
  Core invocation semantics. It only appears in Core's action hash, where Rust derives it as a
  deterministic ABI, never from binding declaration order. Principle: if reordering
  declarations cannot change behavior, it must not change identity. This is unrelated to the
  order of guards and effects, which is Core evaluation semantics.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Author a state machine that runs as ordinary behavior (Priority: P1)

A behavior author declares a state machine over one enum-typed field of an entity, whose enum
cases are the machine's states. The author declares its entry states and its named transitions
(source states, target state, optional guards, inputs, extra effects, postconditions and
command emissions). They build it into a Behavior
module and run it through the public Behavior engine. A transition succeeds only from a declared
source state when its guards hold. In every other case the normal Core denial or evaluation-error
outcome is returned. Core has no state-machine concept.

**Why this priority**: This is the minimum useful product: a readable state-machine authoring
abstraction whose behavior is enforced entirely by ordinary Core semantics. Everything else
(identity, ownership, composition) protects or explains this result.

**Independent Test**: Author the purchase-request machine (Draft → Submitted → InReview →
Approved/Rejected, entry state Draft, `approve` guarded by "actor is the request's approver").
Build it, admit it through the public engine and invoke every transition from every state.
Then inspect the admitted module for any model-specific construct.

**Acceptance Scenarios**:

1. **Given** a request in InReview and an actor who is its approver, **When** `approve` is
   invoked, **Then** the request's status becomes Approved and any declared extra effects and
   command intents are part of the same ordinary transition.
2. **Given** a request in Draft, **When** `approve` is invoked, **Then** Core returns its
   ordinary precondition denial, state is unchanged and no state-machine-specific outcome
   exists.
3. **Given** a request in InReview and an actor who is not its approver, **When** `approve` is
   invoked, **Then** Core returns its ordinary denial for the failed guard.
4. **Given** a transition guard whose evaluation fails (for example an evaluation error inside
   the guard expression), **When** the transition is invoked, **Then** Core's ordinary
   evaluation-error outcome is returned.
5. **Given** the admitted lowered module, **When** it is inspected, **Then** it contains only
   ordinary entities, enums, actions, reads, requirements, effects, postconditions, queries and
   command intents. Nothing names or depends on a state machine.
6. **Given** a transition with source set {A, B} and target C, **When** it is lowered, **Then**
   the resulting action requires the subject's state to be A or B, sets the state to C exactly
   once and ensures the state is C.

### User Story 2 - A state machine cannot be silently bypassed (Priority: P1)

A behavior author combines a state machine with hand-written behavior in the same module. The
build rejects any hand-written action that writes the machine-owned state field. It also rejects
any entity creation that could start the subject in a non-entry state. Without this, a correct
`approve: InReview → Approved` could coexist with an ordinary action doing `Draft → Approved`. The
machine would then only be a set of helper functions, not a model of allowed state transitions.

**Why this priority**: Ownership is what makes the state machine a model rather than a
convenience. It is required for the very first version and must not be deferred.

**Independent Test**: Build a module containing the purchase-request machine plus a hand-written
`force_approve` that sets the status directly, and check that the build fails with an
ownership error that names the action and the field. Then build creation operations initializing
the status to Draft (accepted), to Approved (rejected) and to a dynamically chosen value
(rejected).

**Acceptance Scenarios**:

1. **Given** a machine owning `PurchaseRequest.status` and a hand-written action that assigns
   that field, **When** the module is built, **Then** the build fails with an unauthorized-writer
   error identifying the action and the owned field. No Behavior IR is produced.
2. **Given** a creation of a `PurchaseRequest` that sets status to an entry state, **When** the
   module is built, **Then** the build succeeds.
3. **Given** a creation that sets status to a non-entry state, or to a value that cannot be
   shown statically to be an entry state, **When** the module is built, **Then** the build fails.
4. **Given** a transition whose extra effects also assign the owned field, **When** it is
   lowered, **Then** lowering fails. The target state is assigned exactly once, by the
   lowering itself.
5. **Given** a hand-written action that only reads the owned field or removes the entity,
   **When** the module is built, **Then** the build succeeds. Reading and removal are not
   ownership violations.
6. **Given** any attempt to disable ownership checking, **When** the module is built, **Then**
   no such option exists in this version.

### User Story 3 - Deterministic identity, provenance and explanation (Priority: P2)

An auditor, a tool or an AI author needs to know which model produced a running behavior. The
generated constructs must explain themselves in model terms, and the same model must always
produce the same behavior. Each successful build yields a model identity (ModelHash), the
resulting Behavior module identity (BehaviorHash) and a lowering receipt. The receipt holds both
identities, the model kind, the model semantic version, the lowerer version and a source map.
The source map links every generated construct back to the model construct that produced it.

**Why this priority**: Determinism and provenance make models auditable and reproducible
(constitution IV and V). They build on US1 but are not needed to demonstrate it.

**Independent Test**: Build the same machine many times with every unordered collection
(entry states, transitions, source-state sets) permuted, and with only display names,
descriptions or comments changed. Compare ModelHash, BehaviorHash and the generated semantic
objects. Then check that each generated action and field maps back to its exact model node.

**Acceptance Scenarios**:

1. **Given** two declarations of the same machine that differ only in the order of unordered
   collections, **When** both are built, **Then** ModelHash, the lowered Behavior IR and
   BehaviorHash are identical.
2. **Given** two declarations that differ only in non-semantic metadata (display name,
   description, documentation, comments, source location), **When** both are built, **Then**
   ModelHash and BehaviorHash are identical.
3. **Given** two declarations with a semantic difference (an entry state, a transition, a guard,
   an effect, a semantic id, the owned field or its enum type), **When** both are built,
   **Then** their ModelHashes differ.
4. **Given** a successful build, **When** the receipt is inspected, **Then** it contains
   ModelHash, model kind, model semantic version, lowerer version, Core Release identity,
   BehaviorHash and the source map. Every generated construct resolves to exactly one model
   node, for example `purchase_request / transition / approve` maps to the generated
   `purchase_request__approve` action (exact encoding fixed in planning).
5. **Given** a change only to source-map or diagnostic information, **When** the module is
   rebuilt, **Then** BehaviorHash is unchanged.
6. **Given** a Core denial for a generated action, **When** tooling explains it, **Then** the
   source map lets it be described in model terms (for example "approve is not allowed from
   Draft"). Core's records still refer only to Core objects.

### User Story 4 - Several models and hand-written behavior compose deterministically (Priority: P2)

An author places several state machines (for different entities, or different fields of one
entity) and hand-written behavior in one Behavior module. Composition is deterministic and
independent of the order in which models are supplied. Every semantic collision is an explicit
error, never last-write-wins.

**Why this priority**: Real domains (and RequestFlow) need more than one model per module.
Order-independent, collision-safe composition is the shared infrastructure future models need.

**Independent Test**: Compose two independent machines plus hand-written actions in every input
order and compare outputs. Then compose two machines claiming the same field, and a machine
whose generated action identity collides with a hand-written declaration, and check the
explicit errors.

**Acceptance Scenarios**:

1. **Given** two independent machines and some hand-written actions, **When** they are composed
   in any order, **Then** the resulting Behavior IR and BehaviorHash are identical.
2. **Given** two machines claiming the same entity field, **When** they are composed, **Then**
   composition fails with a conflicting-ownership error naming both models and the field. The
   error is the same for every input order.
3. **Given** a generated declaration whose identity collides with a hand-written or other
   generated declaration, **When** they are composed, **Then** composition fails with a
   collision error instead of overwriting either.
4. **Given** two models contributing incompatible definitions of the same enum or field,
   **When** they are composed, **Then** composition fails with an explicit incompatibility
   error.
5. **Given** two independently authored machines that both define a transition `submit`,
   **When** they are composed, **Then** composition succeeds with two distinct generated
   actions (one per machine), and neither machine had to be renamed.

---

### User Story 5 - The foundation carries a future RequestFlow without Core changes (Priority: P3)

The architect of the next model (RequestFlow) can express the request lifecycle as a generated
StateMachine plus ordinary behavior, using only the infrastructure from this feature. That
lifecycle is Draft → Submitted → InReview → {Approved, Rejected, NeedsChanges}, with
NeedsChanges → Submitted via `resubmit`. StateMachine stays free of request-specific concepts.

**Why this priority**: It validates that the infrastructure is general, but no RequestFlow is
delivered here.

**Independent Test**: Express the RequestFlow reference lifecycle, including its cycle, as a
StateMachine produced by a small test-only generator. Compose it with request creation, which
the generator emits as an ordinary create action. Build it, admit it through the public engine
and exercise the cycle. Confirm that nothing in StateMachine or the shared lowering
infrastructure mentions requests, approvals or assignees.

**Acceptance Scenarios**:

1. **Given** the RequestFlow reference lifecycle, **When** it is generated as a StateMachine
   and built, **Then** it lowers to ordinary Behavior IR that Core admits, and the
   return/resubmit cycle works.
2. **Given** the StateMachine and shared lowering definitions, **When** they are reviewed,
   **Then** they contain no request-specific concepts.

### Edge Cases

- **Pure self-transition** (A → A with no other effect or command): rejected at build time as a
  no-op transition. A self-transition with another meaningful effect or command intent is
  allowed.
- **Terminal state** (no outgoing transitions), **state with no incoming transitions**,
  **state unreachable from entry states**: reported as non-blocking diagnostics only, never as
  errors.
- **Structural reachability vs. real reachability**: a state may be reachable in the graph but
  never entered because a guard can never hold. Graph analysis is conservative tooling and makes
  no verification claim. Proving guard satisfiability is not required for admission.
- **Empty source-state set, a source, target or entry state that is not a case of the owned
  field's enum, duplicate transition id**: blocking build errors.
- **State field is not an enum type (`WType::Enum`; `Option` and Core nominal types are rejected)**: blocking build error. There is no separate state
  declaration that could disagree with the enum.
- **Enum case with no transitions and not an entry state**: valid, and at most a non-blocking
  diagnostic. The machine still owns the field, so such a case can only be held by historical
  entities.
- **Entity creation**: not a transition. A module whose machine has no creation of the subject
  type at all is valid, for example when entities are created elsewhere or already exist. Every
  creation that does exist is checked against the entry states.
- **Entity removal**: not a transition. Existing Core removal semantics apply unchanged.
  Domain states such as Cancelled or Archived are ordinary states if the domain wants them.
- **Historical entities**: existing persisted entities may already be in any valid state.
  Entry-state rules apply only to new creation, and history and migration semantics are
  unchanged.
- **Two transitions sharing a source state**: allowed. Which one runs depends only on which
  capability is invoked externally, never on declaration order.
- **Lambda/closure identity, dictionary insertion order, object identity, memory addresses,
  array indices, time, randomness, environment**: must never influence ModelHash, generated
  identifiers, Behavior IR or BehaviorHash.
- **Generated identifier collision** between differently named constructs after encoding: a
  blocking error (the encoding must be collision-safe, and a detected collision must never be
  resolved silently).
- **A required construct seems impossible to lower faithfully to existing Core semantics**: work
  stops. The requirement and the reason it cannot be lowered are reported, with an assessment of
  whether it is semantic necessity or model convenience. No Core change is made within this
  feature.

## Requirements *(mandatory)*

### Functional Requirements

**Common model lowering contract**

- **FR-001**: Each model kind MUST declare an explicit model semantic version and lowerer
  version. Lowering of an admitted model MUST yield either an ordinary Behavior module or a typed
  model error, never a partial module. Version identifiers identify semantic functions, not
  source-code releases. The model semantic version MUST change when the meaning or admitted
  structure of the model language changes. The lowerer version MUST change when the same model
  contract intentionally lowers to different Core IR. For a fixed (model kind, model semantic
  version, lowerer version, Core Release identity, ModelHash), BehaviorHash MUST be immutable.
- **FR-001a**: The quality gates (`scripts/gates.sh`) MUST enforce FR-001 through golden
  fixtures kept under a versioned manifest (model semantic version, lowerer version, exact Core
  Release identity, and per case ModelHash and BehaviorHash). The gates MUST fail when
  implementation output differs from the fixtures. They MUST also fail when an already
  established version tuple maps to a different BehaviorHash than before, for example by
  comparison against the merge base or a manifest of established mappings, even if the
  expected value in the fixture was edited. A changed mapping is accepted only together with a
  change to the relevant version identity.
- **FR-002**: Lowering MUST be deterministic. Semantically identical models MUST give
  identical lowered Behavior IR and identical BehaviorHash.
- **FR-003**: Lowering MUST be pure. It MUST NOT depend on time, randomness, filesystem
  enumeration, process identity, network, environment, hash-map iteration order or source
  declaration order of unordered collections.
- **FR-004**: Lowering MUST be complete. Every semantic concept a model introduces MUST appear
  in the lowered Behavior IR, and nothing about the model is needed at runtime.
- **FR-005**: The lowered module MUST pass ordinary Core admission and use only public,
  supported Core semantics, reached through the public Behavior engine of the pinned Core
  Release.
- **FR-006**: Lowering MUST operate on a typed, resolved model representation. Binding
  conveniences (language syntax, insertion order, object or lambda identity) MUST NOT become
  model semantics. The resolved representation is ecosystem-only and never reaches Core.
  Open-ended transition parts (guards, extra effects, postconditions, command emissions) MUST
  enter as typed ordinary Core semantic fragments whose free variables refer to declared
  semantic parameter identities. Lambdas, binding objects, raw Wire JSON and any
  model-specific expression language MUST NOT be accepted as model semantics. A transition's
  inputs and context parameters are finite mappings `ParameterId → Type`, not sequences.
  Reordering their declarations MUST leave ModelHash, the lowered IR and BehaviorHash
  unchanged. Where Core needs an ordered parameter vector, Rust MUST derive it by canonical
  order of semantic parameter identity (in v1, the parameter name), never from binding
  declaration order.
- **FR-007**: One binding-neutral Rust model crate in this repository, depending only on the
  public `behavior-engine`, MUST be the single authority for every model kind's resolution,
  normalization, semantic validation, canonical encoding, ModelHash, composition and ownership
  checks, lowering and source-map production. Bindings MUST only construct authoring input and
  source metadata. They MUST NOT decide canonical order, duplicate handling, generated
  identifiers, ownership, defaults or normalized sets. Any binding-side checks are
  non-authoritative ergonomics. Every binding, present and future, MUST call this one
  implementation.

**Identity, receipt and source map**

- **FR-008**: Each admitted resolved model MUST have a content-addressed ModelHash covering
  domain, model kind, model semantic version and the canonical model. It MUST include all
  semantic information, including the semantic identity of an owned field's type rather than a
  copy of its cases, and, for Core fragments, their canonical Core semantic identity under the
  pinned Core version rather than the authoring syntax that produced them. It MUST exclude
  non-semantic metadata (comments, documentation, source
  location, display names and descriptions, editor metadata, ordering of unordered sets).
- **FR-009**: For a fixed (model kind, model semantic version, lowerer version, Core Release)
  and identical ordinary hand-written behavior, equal ModelHashes MUST imply equal
  BehaviorHashes of the composed modules. BehaviorHash covers the whole module, so changing
  unrelated hand-written behavior changes it without changing ModelHash. The converse is not
  required.
- **FR-010**: A successful build MUST produce a lowering receipt containing ModelHash, model
  kind, model semantic version, lowerer version, exact Core Release identity, BehaviorHash and
  source map. The receipt is
  build provenance only and MUST NOT become part of Core runtime semantics.
- **FR-011**: The source map MUST trace every generated Core construct to the model construct
  that produced it. It MUST NOT carry semantic authority, and changing only source-map or
  diagnostic data MUST NOT change BehaviorHash.
- **FR-012**: Model constructs MUST separate stable semantic ids from display names and
  descriptions. Generated Core identities MUST derive only from semantic ids.
- **FR-013**: Generated identifiers MUST be deterministic, derived from (model semantic id,
  construct kind, construct semantic id) with a collision-safe canonical encoding. They MUST
  NOT depend on position, memory address, random values, object identity or time. A
  transition's generated action name MUST be an injective encoding of (machine semantic id,
  transition semantic id), valid under Core's action-name grammar. Distinct pairs MUST always
  give distinct names, and a bare transition id MUST never be used as the action name.
  Independently authored machines MAY therefore use the same local transition ids. In v1 the
  construct kind is implied for action names, because only transitions generate actions. A
  model kind that generates actions from more than one construct kind MUST include the kind in
  its encoding.

**Composition and ownership**

- **FR-014**: Composition MUST accept several models plus hand-written Behavior constructs
  into one Behavior module. The result MUST be independent of the order in which an unordered
  set of models is supplied.
- **FR-015**: Composition MUST NOT use last-write-wins. It MUST fail with explicit errors for:
  duplicate generated identities, generated declarations colliding with hand-written ones,
  incompatible enum or field contributions, and two models claiming exclusive ownership of the
  same field.
- **FR-016**: A model MUST be able to declare exclusive ownership of an entity field.
  Ownership is a build-time ecosystem concept and MUST NOT add semantics to Core.
- **FR-017**: The final composition MUST check every ordinary write to an owned field. Only
  the owning machine's generated transitions, and creations that initialize the field to an
  allowed entry state, are legal writers. Any other writer MUST fail the build.
- **FR-018**: No option to bypass ownership checking MUST exist in this version.

**StateMachine model**

- **FR-019**: A StateMachine MUST target exactly one entity type and one of its fields, which
  MUST have an enum type (`WType::Enum`, not `Option` and not a Core nominal type) `T_f`. The machine's state domain MUST be derived as
  `Q := Cases(T_f)` and MUST NOT be declared separately, either in the model or as semantic
  input from a binding. Every source state, target state and entry state MUST be a case of
  `T_f`. Several machines on different fields MAY share one enum type. Subset state domains are
  out of scope for v1.
- **FR-020**: A StateMachine MUST declare one or more entry states, `Q_entry ⊆ Q`.
- **FR-021**: A StateMachine MUST NOT generate creation actions and MUST NOT represent creation
  as a transition from an implicit nonexistence state. Entry states constrain every ordinary
  creation of the subject entity type in the composed module, whether hand-written or
  contributed by another model. Each such creation MUST initialize the owned field to a
  statically identifiable entry state. A creation that could produce a non-entry or dynamically
  chosen state MUST be rejected at composition unless every possible value is shown to be an
  entry state. In v1, only a literal entry state counts as shown; any computed value is
  rejected.
- **FR-022**: Each transition MUST have a stable semantic id, a non-empty set of source
  states, a target state and a subject binding. It MAY have inputs, context use, extra
  requirements, extra effects, postconditions and command emissions, all of which are typed
  ordinary Core fragments (FR-006).
- **FR-023**: Each transition MUST lower to an ordinary action that: requires the subject's
  state to be one of the source states; then applies the extra requirements under normal Core
  action semantics; sets the owned field to the target state exactly once; applies the extra
  effects and command emissions; and ensures the target state together with any declared
  postconditions. Conceptually: `requires(state ∈ F_t); G_t; set(state, q_t); E_t;
  ensures(state = q_t); P_t; K_t`. Only `requires(state ∈ F_t)`, `set(state, q_t)` and
  `ensures(state = q_t)` are generated by the machine. The rest are the author's Core fragments,
  placed unchanged.
- **FR-024**: Every transition fragment MUST pass two validation layers. The first is Core
  validity in the transition's declared subject, input and context environment: guards and
  postconditions are Bool predicates, effects are Core effects, and commands are Core command
  intents. The second is StateMachine admissibility: fragments refer only to declared bindings,
  and extra effects MUST NOT write the owned field. A fragment failing either layer MUST fail
  lowering with a typed model error.
- **FR-025**: A transition invoked from a non-source state, with a false guard or with a guard
  evaluation error MUST produce exactly Core's ordinary denial or evaluation-error outcome. No
  state-machine-specific outcome, error code or runtime error system MUST be introduced.
- **FR-026**: A pure self-transition (source and target equal, with no other effect or command
  intent) MUST be rejected. A self-transition with another meaningful effect or command intent
  MUST be allowed.
- **FR-027**: Entry states, transitions and source-state sets MUST be unordered. Their
  declaration order MUST NOT affect ModelHash, Behavior IR or BehaviorHash.
- **FR-028**: The StateMachine MUST NOT schedule, trigger, queue, time, retry or orchestrate
  transitions, and MUST NOT keep its own event log. A transition happens only when its
  generated capability is invoked externally. History is Core's ordinary history.
- **FR-029**: Entity creation and removal MUST remain ordinary Core lifecycle semantics. The
  StateMachine governs only state evolution of existing subject entities, and neither creation
  nor removal is modelled as a transition.
- **FR-030**: The build MUST report blocking errors for at least: a source, target or
  entry state that is not a case of the owned field's enum, empty source-state set, duplicate
  transition id, state field that is not an enum type, owned field written by
  transition effects, unauthorized writer to an owned field, conflicting ownership, pure
  self-transition and generated identity collision.
- **FR-031**: The build MAY report non-blocking diagnostics for unreachable states, states
  without incoming or outgoing transitions and transitions unreachable from entry states. These
  MUST NOT block a build and MUST NOT be presented as verification results.
- **FR-032**: StateMachine and the shared lowering infrastructure MUST stay free of
  domain-specific concepts (requests, approvers, assignees), so that a future RequestFlow can
  generate a StateMachine plus ordinary behavior.

**Authoring API**

- **FR-033**: The first binding API (Python, exposed through `behavior-py`) MUST let a machine
  and its transitions be declared readably, using semantic ids and state names rather than
  generated Core plumbing. It MUST be a thin authoring layer that hands model input to the Rust
  model crate (FR-007).

**Boundaries and process**

- **FR-034**: This feature MUST NOT change behavior-ir-core, its semantics, public API or Wire
  IR, and MUST NOT introduce a new Core primitive. If a Core change appears necessary, work MUST
  stop and the case MUST be reported (the concrete StateMachine requirement, why existing Core
  constructs cannot lower it faithfully, and whether it is necessity or convenience) for a
  separate Core feature on a branch chosen by the maintainer.
- **FR-035**: Before implementation starts, planning MUST produce `plan.md`, `data-model.md`,
  `contracts/lowering-contract.md`, `contracts/state-machine-contract.md`,
  `contracts/identity-and-source-map.md` and `tasks.md`. Planning MUST answer, with evidence:
  (1) which public Behavior construction APIs build every required lowered object;
  (2) how final-module composition enforces field ownership and entry states;
  (3) which existing semantic identifiers can be reused for generated identities;
  (4) whether ModelHash needs a new ecosystem-only canonical encoding;
  (5) that no Core change is needed.
  Check (1) is a planning gate. If the public `behavior-engine` cannot build some ordinary IR
  that StateMachine needs, planning MUST stop and classify the gap in one of two ways. Either a
  Core capability that already exists is not exposed publicly, which needs an additive public
  API exposure. Or StateMachine needs semantics Core cannot express, which needs a separate Core
  semantic feature. Both are Core changes under FR-034. Moving authority to a binding is never
  an acceptable fallback.
- **FR-036**: The model rules in `models/README.md` MUST be brought in line with this
  feature. The existing Python example in `models/examples/state_machine/` MAY remain as a
  worked example or reference fixture, but MUST NOT remain a second authoritative StateMachine
  lowering once the Rust model crate exists.

### Key Entities

- **Behavior Model**: an authoring abstraction of a given kind with a model semantic version.
  It lowers completely to ordinary Behavior IR.
- **Model Input**: what a binding builds from authoring syntax, plus source metadata such as
  locations. It is not yet resolved or normalized and has no semantic authority.
- **Resolved Model**: the typed, canonical, binding-independent representation produced from
  Model Input by the Rust model crate. It is the only input to hashing and lowering and is never
  seen by Core.
- **StateMachine**: `(E, f, Q_entry, 𝒯)`: subject entity type, owned enum field, entry-state
  set and transition set, with a stable semantic id. Its state domain is derived from the
  field's enum and is not stored on the machine.
- **Transition**: `(F_t, q_t, G_t, E_t, P_t, K_t)`: semantic id (local to its machine),
  source-state set, target state, subject binding, and optional inputs and context use. Its
  guards, effects, postconditions and command emissions are typed Core fragments, not model
  constructs. It also has optional display metadata.
- **Ownership claim**: a model's exclusive claim to an entity field, checked at composition.
- **ModelHash**: content identity of a resolved model, covering only semantic content.
- **Lowering Receipt**: ModelHash, model kind, model semantic version, lowerer version, Core
  Release identity, BehaviorHash and source map. Build provenance only.
- **Compatibility Fixture Manifest**: per (model semantic version, lowerer version, Core
  Release identity), the established ModelHash → BehaviorHash mapping of each reference case.
  It is an executable contract that the gates check, not a snapshot that may be overwritten.
- **Source Map**: links between generated Core constructs and the model constructs that
  produced them. It has no semantic authority.
- **Model Error / Diagnostic**: typed blocking errors that stop a build, and non-blocking
  diagnostics that only inform.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For every state × transition pair of the reference purchase-request machine,
  invoking the transition through the public engine succeeds exactly when the state is in the
  transition's source set and its guards hold. Otherwise it returns Core's ordinary outcome.
  This holds in 100% of pairs.
- **SC-002**: Across at least 1,000 randomized permutations of every unordered collection, and
  of the order in which models are supplied, ModelHash, generated semantic objects and
  BehaviorHash are identical in 100% of runs.
- **SC-003**: Changing only display names, descriptions, comments or source-map data changes
  neither ModelHash nor BehaviorHash in 100% of tested cases. The
  same holds for guards or effects written in different authoring syntax that produces
  identical Core semantics. Every tested semantic change
  changes ModelHash.
- **SC-004**: 100% of ownership-negative cases are rejected at build time with an error naming
  the offending construct and the owned field. These cases are: a hand-written writer, a
  transition effect writing the owned field, a non-entry or dynamic creation, and two machines
  claiming one field. No Behavior IR is produced in any of them.
- **SC-005**: Every generated construct in the reference machines maps through the source map
  to exactly one model node, and every model transition maps to exactly one generated action.
- **SC-006**: The lowered modules contain zero model-specific constructs, run only through the
  public Behavior engine, and are admitted without any Core change. The pinned Core Release and
  behavior-ir-core repository are untouched.
- **SC-007**: The RequestFlow reference lifecycle, including its return/resubmit cycle, is
  expressible as a StateMachine plus ordinary behavior and runs end-to-end with no change to
  StateMachine, the shared infrastructure or Core.
- **SC-008**: Every blocking error listed in FR-030 has at least one test producing it, and
  each non-blocking diagnostic in FR-031 leaves the build successful.
- **SC-009**: A deliberate test change that alters lowered output without a version bump is
  rejected by the gates in 100% of tested cases. This includes the case where the fixture's
  expected value was also edited. The same change with the correct version bump passes.

## Assumptions

- The feature lives in the behavior-ir ecosystem repository, depends only on the public
  `behavior-engine` of the Core Release pinned in `core-release.json`, and follows the
  constitution's rules for models and bindings.
- The authoritative model implementation is one Rust crate in this workspace, for example
  `crates/behavior-models`, with the dependency chain `behavior-py` → model crate →
  `behavior-engine`. `behavior-py` may still use `behavior-engine` directly for ordinary Core
  APIs. The crate is not split per model or per concern until later models (RequestFlow,
  Approval) show that a split is needed. Python is the first binding.
- "Ordinary Behavior IR" means the constructs Core already supports: entities, enums,
  actions, reads, requirements, effects, postconditions, queries and command intents. The
  planning check (FR-035) is expected to confirm that these are sufficient.
- Entry-state and ownership rules apply to all creations and writes in the composed module,
  whether hand-written or generated by another model.
- "Guard evaluation error" uses whatever expression Core already defines to produce an
  evaluation error. No special failing construct is introduced for testing.
- Graph diagnostics are informational and need no particular output format beyond being
  distinguishable from errors.
- Out of scope: new Core primitives, new Wire IR, a state-machine runtime, event queues,
  orchestration, timers, scheduling, BPMN, Petri nets, hierarchical or parallel states,
  distributed execution, automatic retries, sagas, new persistence or command semantics, a
  generic workflow engine, and RequestFlow itself.
