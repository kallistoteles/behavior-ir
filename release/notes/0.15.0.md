# Behavior 0.15.0

Behavior 0.15.0 adopts published Core 0.16.0 at immutable commit
`63a8c164523275e06ac1d7dc5330db4a899c9d99`, with verifier 0.11.0 and Z3 4.16.0.
The minor version follows the existing policy for changed verifier outcomes.

## Consumer changes

- **Ref-target removal verification (Core 030).** Supported guarded free removal,
  joint referrer/target removal and retarget/removal now produce complete-world reference
  preservation checks in profiles 0.7 and 0.8. Require nonempty `reference_world` checks,
  actual proven outcomes and the complete selected report. All incoming fields/types matter;
  runtime reference integrity remains independent. Unsupported effect/binding shapes and
  exhausted solver budgets remain inconclusive, never proven. See the executable
  [removal example](../../skills/behavior-verification/examples/reference_removals.py).
- **Growing Stores with global rules (Core 029).** Supported count-bound changes can retain
  validated state across transactions on one Store. The frozen native Python comparison
  measured approximately 42% lower complete transaction-window cost at 1,024 live entities
  than the published 0.14.0 wheel. Creation 1,000 succeeds and 1,001 refuses under a genuine
  maximum-1,000 invariant. This is measured finite capacity, not constant-time performance:
  complete outputs, unsupported dependencies, reopened Stores and continuity changes can
  retain population-dependent work. See [measurement evidence and limits](../../specs/512-adopt-core-update/evidence/README.md).
- **Fresh governance evidence.** Select released verifier-0.11 policies explicitly.
  Existing verifier-0.10 policies and archived evidence retain their original meaning;
  they do not gain current authority automatically. Content caches remain scoped to the
  exact module, action, selected profile and verifier contract.
- **Fresh Safety evidence.** Recertify against the new Core identity. A previous-Core bundle
  remains archival data and cannot become a fresh certificate by being loaded or hashed.
  Lean generic/concrete checking, permitted-axiom audits and fresh kernel checking remain
  mandatory. Policy semantics v1, checker 3, statement 2 and evidence/bundle v2 are unchanged.

## Compatibility and boundaries

StateMachine, RequestFlow, Approval, WorkQueue and composition retain their meanings and
established identities. Historical compatibility entries and receipt baselines remain intact;
new exact-Core tuples are appended. The complete reference semantic snapshot is unchanged.
Current Skills identify this release and preserve the distinction between local SMT proof,
Safety induction, tests and host assumptions.

No Core runtime semantics, Store formats or replay requirements are added. Safety policies
remain state-transparent build-time artifacts. LifecycleDependency v1 still requires immutable
ownership and its restricted operation/guard pattern; stronger Core verification does not
expand that language. Genesis, migration and exact-boundary module authorization remain
separate obligations. Ordinary retry after a conflict requires re-evaluation; recovery after a
lost acknowledgement must first establish whether the original commit occurred.

This feature prepares a release candidate. Publication follows merge and a separate explicit
request through the existing annotated-tag process. Previously published artifacts are immutable.
See [Feature 512 evidence](../../specs/512-adopt-core-update/evidence/README.md) for actual
acceptance status, source/artifact identities and nonblocking limitations.
