# Candidate comparison contract

The G1 route is selected in [design-decision.md](../../design-decision.md). These isolated
experiments preserve both successful and exhausted alternatives; they never issue library
certificates. Complete installed A256/A512 and mixed smoke passed, while final repeated
capacity/delivery acceptance remains tracked separately. The sections below describe the
comparison protocol established before selection.

## Separate interventions

1. Data construction: current canonical values with factored/bounded-depth definitions versus a
   compact exact representation with a checked interpretation. Current byte/chunk syntax is not
   protected, but full semantic identity and complete module/policy coverage are.
2. Finite premises: verified direct checks versus fallible producer proposals checked by fixed
   sound templates. Separate full-key uniqueness, permission lookup and remaining well-formedness/
   lifecycle obligations so a data improvement cannot conceal a second proof bottleneck.
3. Actual fresh dependency closure: measure narrower explicit imports only if the complete theorem
   and axiom/replay contract remain intact. Compiled dependencies or previous acceptance cannot
   replace required fresh kernel checks.

Test data and finite-check interventions individually, then combined. Measure complete construction
and independent checking; native execution is diagnostic only. Retain all unsuccessful variants.

## Candidate proof routes to compare

- Direct uniqueness: existing verified `List.mergeSort_perm`, uniqueness transfer and appropriate
  comparison laws, with a checked bridge for strict adjacency/global uniqueness if used. No
  unproved custom sorting implementation is needed for proof authority.
- Proposed ordering/index data: an untrusted producer can suggest an ordering or inverse-index
  mapping. The checker must establish full multiplicity coverage and strict original-key uniqueness
  itself. Bounds, inverse relationships and key bindings cannot be accepted as producer assertions.
- Permission membership: evaluate existing lawful set membership results or checked index witnesses.
  Pinned `Array.mem_of_getElem?`, `Array.mem_toList_iff` and `List.contains_iff_mem` provide potential
  bridges from a checked exact indexed value to original list permission. Ordinary Core action
  order, independent creator/writer/remover permissions and intersection across all policies remain.

A proposed data witness is not executable Lean source or an olean payload. All proof code/templates
are trusted installed sources; only a bounded typed grammar can cross the evidence boundary.

## Interpretation and nonvacuity

Changing finite input representation needs a kernel-checked interpretation/refinement to the
required semantic guarantees. Compare actual statement types, not just theorem names. Retain the
explicit Rust/Core extraction, encoding and guard-probe correspondence boundary; canonical JSON
hashes or reflexive equalities do not prove that extraction implements Core semantics.

Every candidate needs a valid positive instance and controls for missing/duplicate keys, wrong
laws/indices, omitted actions/operations/policies, unauthorized roles, wrong guard binding and
changed identities. A failed producer may not cause false acceptance; a valid independently produced
proposal may pass. Retain the twelve mapped baseline obligations and any new soundness/bridge roots,
allowed transitive axioms and complete fresh replay. No result here can be called certification until
all exact-instance checks finish through the library authority.
