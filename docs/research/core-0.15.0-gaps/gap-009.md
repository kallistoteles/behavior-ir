# Draft Core issue — Ref-target removal is inconclusive before SMT encoding

For review only. Proposed layer: Core verifier. Priority: verification coverage investigation.
Baseline and commands: [README](README.md). Minimal public authoring case:

```python
@entity
class Target:
    value = field(int)

@entity
class Holder:
    target = field(Ref[Target])

@action
def remove_free(target: Target):
    requires(not_(referenced(target.id)))
    remove(target)
```

Admit both entities and this single action, then call
`verify(model, Profile(checks=["preservation"]))` using the pinned solver.
No Holder instance, entity invariant or second action is required to trigger the restriction.

## Actual versus expected

Expected investigation target: verify the guarded, reference-safe deletion while preserving
Core's existing complete resulting-state and error semantics.

Actual: the overall attestation is `not_verified`. Its one preservation check is
**`inconclusive`, reason `encoding_error`**, with the exact explanation:

```text
cannot encode: complete-world reference obligations for removal target
```

This is a conservative inability to encode, not a counterexample, false `Verified` or demonstrated
runtime soundness defect. In `ActionEncoding::build()` a removed type with any declared incoming
Ref field returns `Unsupported` before the encoder constructs the action environment. Consequently,
guard formulation or a larger solver budget cannot bypass this particular production branch.
The code explains that a single referenced Boolean does not represent the full-world reference
obligations and canonical first-failure schedule.

Source: [exact encoder restriction](https://github.com/kallistoteles/behavior-ir-core/blob/v0.15.0/crates/behavior-verify/src/encode.rs#L1325).

## Actual Core execution controls

Every case uses a separate single-action module and a fresh Store.

| Case | Runtime | Verifier preservation |
| --- | --- | --- |
| Guarded deletion, no Holder instances | ALLOW, commit position 1 | Inconclusive |
| Guarded deletion, surviving Ref | DENY, no commit | Inconclusive |
| Unguarded deletion, surviving Ref | DENY, no commit | Inconclusive |
| Create surviving Ref and remove its target together | DENY, no commit | Inconclusive |
| Remove referring Holder and Target together | ALLOW, commit position 1 | Inconclusive |
| Retarget Holder to another existing Target, then remove old Target | ALLOW; stored Holder points to new target | Inconclusive |
| Replace Ref with ordinary Id and keep the Holder | ALLOW even when Target is deleted | `verified`, zero applicable preservation checks |
| Remove Holder declaration entirely | ALLOW | `verified`, zero applicable preservation checks |

The last two are schema/obligation controls, **not SMT proofs of equivalent reference safety**.
A separate positive solver control updates a constrained Target to 1 and actually proves its
nonnegative-value preservation obligation. This avoids treating an empty check list as proof.
Data and behavior replay assertions pass for all short runtime histories.

## Requirements for further work

- Formalize complete resulting-state reference integrity and the relevant ordered error
  semantics before selecting a symbolic representation. Preserve public runtime behavior.
- Cover unbound referring entities, required and optional references, creation/removal/retargeting,
  aliases and simultaneous changes. Source-state `referenced` alone is not a resulting-state proof.
- Supported safe cases should discharge the intended obligations. Violated obligations and
  unsupported cases must not become false proofs; any claimed counterexample needs concrete
  confirmation through actual Core execution.
- Keep generic theorem/encoding correspondence, solver results, runtime tests and residual
  assumptions explicit. No finite set of passing examples establishes general encoder soundness.

Replacing `Ref` with `Id` is not a drop-in workaround: the runtime controls demonstrate that it
permits a surviving Holder whose target no longer exists. No alternative equivalent workaround
was established. Application-specific redesign and unrelated `unique(Option)` work are out of scope.
