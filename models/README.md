# Behavior Models

A **Behavior Model** is a higher-level modeling abstraction, such as a state machine, a workflow,
an approval process or a saga. It lowers completely to ordinary Behavior IR.

**Behavior IR is the semantic assembly language; models are languages above it.** The core
admits the lowered IR like any other module and never learns which model produced it:
`Meaning(M) := Meaning_Core(Lower(M))`. See the core's
[ARCHITECTURE.md](https://github.com/kallistoteles/behavior-ir-core/blob/v0.13.0/ARCHITECTURE.md)
for the layers and the dependency direction.

## The model authority

[`crates/behavior-models`](../crates/behavior-models) is the **single authority** for every model
kind (feature 501). It owns resolution, normalization, validation, canonical identity
(ModelHash), composition and ownership, generated names, lowering, receipts and source maps. It
depends only on the public `behavior-engine`.

Bindings only describe what the author wrote and trace Core expressions inside scopes the model
crate opens. The Python syntax is in [`python/behavior/models.py`](../python/behavior/models.py).
A binding never sorts, deduplicates, defaults, renames or validates model semantics.

The full contracts are in
[`specs/501-model-lowering-state-machine/contracts/`](../specs/501-model-lowering-state-machine/contracts/).

## Rules

1. **Complete, deterministic lowering.**
   - A model lowers to ordinary Behavior IR. The same model always gives the same IR and the
     same BehaviorHash. Lowering reads no clock, randomness, environment or source order.
   - A model may restrict, compose or generate core semantics. It never introduces runtime
     semantics the core does not know: no model-specific evaluation, hook, error or side
     channel.
2. **One authoritative lowering.** Each model kind has exactly one implementation, in
   `behavior-models`, and every binding calls it.
3. **What cannot be lowered faithfully.** A construct that Behavior IR cannot represent
   faithfully is never implemented as hidden model behavior. Either it is redesigned on
   existing core semantics, or the missing concept is proposed as a core primitive (a core
   feature numbered 012+). The model waits for the Core Release that adds it. Inconvenience is
   not evidence of a missing primitive.
4. **Model identity.**
   - `ModelHash` is the content hash of a canonical document of semantic facts only. Display
     names, descriptions, source locations and authoring order never change it.
   - A model's identity depends on exactly the declarations it references, by their Core
     declaration identity: its subject, actor and state-binding entities, and every enum,
     nominal and entity its parameter and payload types mention. Nothing else in the module
     affects it. This is exact dependency, not behavioral equivalence: adding a field the model
     never uses to a referenced entity changes the ModelHash (feature 505).
   - Every build returns a receipt: ModelHash, model kind, model semantic version, lowerer
     version, exact Core Release, BehaviorHash, the canonical document and a source map.
   - The module hash is always authoritative for runtime semantics.
5. **Versions identify functions.** For a fixed (model kind, model semantic version, lowerer
   version, Core Release, and the versions of any embedded model), the ModelHash → BehaviorHash
   mapping of the reference cases in
   [`fixtures/compat.json`](fixtures/compat.json) is immutable. The gate `models compat` rejects
   any change that is not accompanied by a version bump. A tuple replaced by a version bump is
   removed only through explicit supersession: the new tuple lists it in `supersedes`, has the
   same model kind and Core Release, a higher version vector and every one of its reference
   cases (`check-models-compat.py --write --supersede`).
6. **Where a concept belongs.** Ask: *must the evaluator understand this construct for its
   semantics to be correct?* If not, it is a model, a library or tooling here. If so, it is a
   candidate core primitive.

## StateMachine

A state machine governs one enum field `f` of an entity type `E`:

```text
SM = (E, f, Q_entry, 𝒯)        Q := Cases(T_f)        Q_entry ⊆ Q
t  = (F_t, q_t, G_t, E_t, P_t, K_t)
```

- **State domain.** The enum defines which values the field can hold; the machine defines which
  changes between them are permitted. There is no separate list of states.
- **Transitions.** Each transition lowers to one ordinary action `<machine id>__<transition id>`
  with the layout below. Only the first requirement, effect and postcondition are generated by
  the machine. Guards, extra effects, postconditions and commands are ordinary Core expressions,
  placed unchanged.

  ```text
  requires  subject.f in F_t ;  G_t
  effects   subject.f := q_t ;  E_t
  ensures   subject.f == q_t ;  P_t
  ```
- **Outcomes.** Invoking a transition from another state, or with a false guard, gives Core's
  ordinary denial. A guard that fails to evaluate gives Core's ordinary evaluation error.
- **Ownership.** No other ordinary action may write `f`, and every creation of `E` must set `f`
  to a literal entry state. The build checks this over the final admitted module, and there is
  no escape hatch.
- **Creation and removal.** These remain Core lifecycle and are never transitions.
- **Not a workflow engine.** The machine never schedules, triggers, queues, retries or
  orchestrates; a transition happens only when its action is invoked.

```python
machine = StateMachine("purchase_request", subject=PurchaseRequest, state_field="status",
                       entry_states={RequestStatus.DRAFT})
machine.transition("submit", from_={RequestStatus.DRAFT}, to=RequestStatus.SUBMITTED)
machine.transition("approve", from_={RequestStatus.IN_REVIEW}, to=RequestStatus.APPROVED,
                   context={"actor": Id[Actor]},
                   requires=[lambda r, actor: actor == r.approver],
                   effects=[lambda r, actor: set_(r.approved_by, actor)])
module = BehaviorModule(entities=[Actor, PurchaseRequest], enums=[RequestStatus],
                        models=[machine])
module.model_receipts      # provenance: ModelHash, versions, BehaviorHash, source map
module.model_diagnostics   # warnings only (terminal or unreachable states), never verification
```

Callables receive the subject, then the inputs, then the context parameters, *by position*, in
the order the model crate chooses: inputs and context sorted by name. Their Python parameter
names do not matter.

Transitions can emit commands (`K_t`). Declare them with `@command`, pass them to
`BehaviorModule(commands=[...])` (which selects Core's command profile), and emit them with
`emits=[lambda r, ...: emit(NotifyRequester, when=..., approver=...)]`. An emission is an intent
recorded with the commit, never an effect.

`module.model_receipts` are typed `LoweringReceipt`s. Their source locations are relative, so
the same model gives the same receipt in every checkout.

### Transition state bindings (feature 507)

A transition may bind further entities with `state={"doc": Document}` and change them atomically
with the status. The bound parameters follow the subject, sorted by name, before the inputs and
context. **A binding never grants authority**: the machine's own field is written only by the
generated status effect through the subject, an authored write of it through any parameter of the
subject's type is `TRANSITION_WRITES_OWNED_FIELD`, and every other model's ownership rules apply
to bound entities unchanged. Binding resolution, aliasing and concurrency are Core's.

**Language levels (research R13).** A machine without bindings is StateMachine semantic version
2, with exactly the established canonical document and mappings. A machine whose transitions bind
is version 3 (`behavior.model.state_machine.v3`, every transition lists `state` with each
entity's declaration identity). RequestFlow follows the same rule (flow 3 with embedded machine
3). Both levels have their own compat tuples; nothing is superseded.

## RequestFlow

A request flow (feature 502) is a persistent request that an actor creates, that carries typed
data, and whose status evolves through a finite set of cases. **RequestFlow owns request
creation and request conventions; StateMachine remains the single authority for status
evolution.**

```text
RF = (id, A, E, Q, Π, 𝒞, 𝒯)       Q := Cases(T_status)      E := EncodeEntityName(id)
c  = (id_c, q_c, S_c, I_c, C_c, G_c, V_c, E_c, P_c, K_c)        Q_entry := { q_c | c ∈ 𝒞 }

L_RF(R) = Compose(Decls(R), Creates(R), L_SM(SM(R)))      SM(R) = (E, status, Q_entry, 𝒯)
```

- **Meaning.** `Meaning(RF) := Meaning_Core(L_RF(RF))`. The flow lowers to one ordinary entity,
  ordinary creation actions, and the transitions of an ordinary StateMachine, lowered by the
  unchanged StateMachine lowerer. There is no second transition semantics.
- **Lifecycle theorem.** A creation sets `status = q_c ∈ Q_entry`, and the embedded machine owns
  every later write of `status`. So every ordinary status trace of a request lies in
  `Q_entry · R_T*`, where `R_T = {(q, q_t) | t ∈ 𝒯, q ∈ F_t}`.
- **The request entity.** It is generated, with fields `requester: Id<A>`,
  `status: T_status`, `assignee: Option<Id<A>>` (when enabled) and the payload, sorted by name.
  Its name is `EncodeEntityName(id)`, an injective encoding (`purchase_request` →
  `PurchaseRequest`, `a_1b` → `A_1b`, `a1b` → `A1b`). The status enum stays an authored
  declaration; the flow references it.
- **Identities, never references.** `requester` and `assignee` are `Id`, not `Ref`. They add no
  existence constraint, reverse reference or removal blocking. A guard that needs the actor to
  exist says so with ordinary `exists(...)`.
- **Creation.** Each creation is one action `<flow>__<creation>`. Its parameters are
  `request_id: Id<E>`, then inputs, state bindings and context, each group sorted by name. It
  holds exactly one `Create E` with `status = q_c`, plus the author's guards, effects (over the
  state bindings, committed atomically with the creation), postconditions and commands. The
  initializer `V_c` must set every field except `status` exactly once; anything else is a static
  `INITIALIZER_*` error. Creation and transition ids share one namespace.
- **Authority is explicit.** Neither `requester` nor `assignee` authorizes anything; write the
  guard (`actor == r.assignee`). There is no clock (`created_at` comes from context), no
  generated identity, no notification beyond ordinary command intents, and no generated reads.

### Ownership

| Field or item | Who may write it |
|---|---|
| request creation | the flow's creation actions only (`UNAUTHORIZED_REQUEST_CREATION`) |
| `status` | the creation (as `q_c`), then the embedded StateMachine only |
| `requester` | the creation only (`UNAUTHORIZED_REQUESTER_WRITE`) |
| `assignee`, payload | any ordinary action |

The checks run over the final admitted module, like the StateMachine's.

### Declaration staging

A RequestFlow contributes a declaration, so hand-written behavior must be able to see it.
`BehaviorModule` builds in four phases
([contract](../specs/502-request-flow/contracts/declaration-staging.md)):

| Phase | What happens |
|---|---|
| P1 | authored enums, nominal types and entities |
| P2 | `declare_models`: each model's contributed declarations, identical-or-error (a no-op for StateMachine-only modules, whose hashes are unchanged) |
| P2b | commands (their payloads may name the request entity) |
| P3 | hand-written derived values, invariants, constraints, actions and reads |
| P4 | `compose`: creations, transitions, the final ownership pass, receipts |

Authored entities may hold `Id[...]` or `Ref[...]` fields of the request entity, because Core
checks declarations together.

```python
S = PurchaseRequestStatus       # an authored enum: Draft, Submitted, InReview, Approved, ...
flow = RequestFlow("purchase_request", actor=User, status=S,
                   payload={"title": str, "amount": int}, assignee=True)
flow.create("create", to=S.DRAFT, inputs={"title": str, "amount": int},
            context={"actor": Id[User]},
            values=lambda request_id, amount, title, actor: {
                "requester": actor, "title": title, "amount": amount, "assignee": None})
flow.transition("approve", from_={S.IN_REVIEW}, to=S.APPROVED, context={"actor": Id[User]},
                requires=[lambda r, actor: actor == r.assignee])

PR = flow.request_entity        # a typed handle: annotations, Id[PR], select(PR)

@action
def retitle(r: PR, *, title: Input[str]):
    set_(r.title, title)

module = BehaviorModule(entities=[User], enums=[S], models=[flow],
                        actions=[retitle])
```

`flow.request_entity` takes its name from Rust; its fields are a view that the build checks
against the schema Rust declares. There is one receipt per flow (`model_kind: "request_flow"`),
and its `embedded` record carries the StateMachine's identity and ModelHash. The source map
links `purchase_request/transition/approve` to `state_machine:purchase_request/transition/approve`
and to the Core action `purchase_request__approve`.

The reference flow is
[`fixtures/rf_purchase_request.py`](fixtures/rf_purchase_request.py).

## Approval

An approval (feature 503) records immutable decisions about an existing subject and derives an
outcome from them. **It never changes its subject**; workflows read its outcome through ordinary
predicates.

```text
AM = (p, S, A, k_A, k_R, Π, approve, reject)      k_A ≥ 1,  k_R ≥ 1 or ⊥
C  := <P>DecisionChoice { APPROVE, REJECT }        X := <P>Decision { actor: Id<A>, choice: C,
                                                                     subject: Id<S>, Π… }
L_AM = Compose(Decl(AM), Defs(AM), Actions(AM))
```

- **Meaning.** `Meaning(AM) := Meaning_Core(L_AM(AM))`: one generated enum, one generated
  entity, five ordinary derived values (`p__approve_count`, `p__reject_count`, `p__approved`,
  `p__rejected`, `p__pending`, each over `s: S`) and two ordinary actions (`p__approve`,
  `p__reject`), each holding exactly one `Create X`. Core never learns what an approval is.
- **Outcome.** `approved = approve_count ≥ k_A ∧ ¬rejected`, `rejected = reject_count ≥ k_R`
  (false when `k_R = ⊥`), `pending = ¬approved ∧ ¬rejected`. REJECTED takes precedence, so the
  three are exclusive and exhaustive on every state, valid or not. A refused attempt is
  **DENIED**; REJECT is a recorded choice and REJECTED a derived outcome.
- **Three layers of terminality.** A decision action requires, in fixed positions, `[0]` Open,
  `[1]` `p__pending(subject)` (the terminal guard), `[2]` Eligible, `[3]` no decision of this
  actor on this subject yet, then the author's guards. Its postconditions check, on the child
  state, `[0]` at most one decision per `(subject, actor)` and `[1]` never both thresholds
  reached (when `k_R ≠ ⊥`). Concurrent attempts are serialized by Core's compare-and-set: a
  stale commit is a `STATE_CONFLICT`, and its retry meets the guards on the new state.
- **Identities, never references.** `subject` and `actor` are `Id`, not `Ref`: a decision
  survives the removal of its subject or actor, and an actor need not exist as an entity.
  Authority is explicit: Eligible is the author's predicate over the actor expression, the
  actor expression is the author's (never inferred from a parameter name), and there is no
  implicit "not the requester" or "the assignee" rule. There is no clock; `decided_at` and
  similar values come from context.

> **Global safety = valid base state + local preservation + complete effect ownership.**
> If a store starts in a state where every subject has at most one decision per actor and never
> both thresholds reached (the base state), every committed decision action preserves that
> (its guards and child-state postconditions), and no other action can create, write or remove
> a decision (ownership, checked over the final module), then every reachable state is valid by
> induction. Seeded states that violate the base state are test fixtures, not Approval states.

### Ownership

| Item | Who may touch it |
|---|---|
| creation of `X` | `p__approve` and `p__reject` only (`UNAUTHORIZED_DECISION_CREATION`) |
| any field of `X` | nobody: decisions are immutable (`UNAUTHORIZED_DECISION_WRITE`) |
| removal of `X` | nobody (`UNAUTHORIZED_DECISION_REMOVAL`) |
| reads, queries, derived values and guards over `X` | anyone |

The check covers every action of the final module, whatever produced it (hand-written,
StateMachine, RequestFlow or another approval).

### Declaration DAG

Approval generalizes P2 to a topological pass: a model that references a type another model
contributes is declared after it (an approval over a flow's request entity, or over another
approval's decision entity). Cycles are `DECLARATION_CYCLE`, a name contributed twice or
already authored is `DECLARATION_COLLISION`, and a hand-written item with a generated
definition's name is `GENERATED_NAME_COLLISION`. Authored declarations may name `X` and `C`
before they exist (law D5). Model sets without edges and definitions build exactly as before.

### Python

```python
review = Approval("purchase_request_approval", subject=PR, actor=User,
                  approve_threshold=2, reject_threshold=1)
review.approve(actor=lambda decision_id, subject, actor: actor, context={"actor": Id[User]})
review.reject(actor=lambda decision_id, subject, actor: actor, context={"actor": Id[User]})
flow.transition("finalize", from_={S.IN_REVIEW}, to=S.APPROVED,
                requires=[lambda r: review.approved(r)])
module = BehaviorModule(entities=[User], enums=[S], models=[flow, review])
```

`review.decision_entity` and `review.choice` are typed handles checked against the schema Rust
declares; `approved`, `rejected`, `pending`, `approve_count` and `reject_count` take a bound
entity of the subject type. There is one receipt per approval (`model_kind: "approval"`) with
its `generated` enum, entity and derived hashes; ApprovalHash references the subject and actor
by Core declaration hash, so a change to either entity changes it.

**Non-goals.** Automatic RequestFlow transitions, ordered stages, approval chains, delegation,
substitute approvers, weighted votes, percentage quorum, "all currently eligible users",
implicit role or manager lookup, deadlines, escalation, timers, withdrawal, decision changes,
abstention, notifications beyond ordinary command intents, external command execution, a second
event log and a second expression language.

## WorkQueue

A work queue (feature 507) governs persistent, claimable units of work: what exists, when it may
be claimed, which worker holds it, which attempt that worker may finish, and how it ends. **It
defines which changes of work state are valid; it never schedules, executes or orders work.**

```text
WQ = (id, A, T, Π, M, G, K)        A worker (Id only)   T ordered nominal time   M ≥ 1
WorkQueue → <E>Status enum, E entity (status, payload…, attempts, owner, lease_until, available_at)
          + invariant ValidWork, derived terminal(w), reads ready(now) and expired(now)
          + <id>__enqueue (creation) + an embedded StateMachine:
            claim READY→LEASED · renew LEASED→LEASED · complete LEASED→SUCCEEDED
            retry LEASED→READY · fail LEASED→FAILED · recover LEASED→READY (expired, attempts < M)
            exhaust LEASED→FAILED (expired, attempts = M) · cancel READY|LEASED→CANCELLED
```

- **Fencing.** A claim increments `attempts`, the claim generation. Renew, complete, retry and
  fail require `owner == worker`, `attempts == generation` and a live lease; their generated
  postconditions are `attempts == generation` (claim: `attempts == expected_generation + 1`).
  After a later committed claim an earlier generation never satisfies these again, through
  ordinary transitions (contracts/safety-arguments.md, SA-FENCE).
- **Trust boundary.** `worker`, `now`, `lease_until` (claim, renew) and `available_at` (retry,
  recover) are host context with fixed names; `generation` and `expected_generation` are caller
  input and only compared. Enqueue, claim (`eligible`), recover, exhaust and cancel need an
  authored authorization guard; a missing one is `MISSING_AUTHORIZATION`.
- **Time.** Core reads no clock. A lease is live or expired relative to the recorded `now` of the
  evaluation; freshness of `now` at commit and clock monotonicity are host assumptions, and no
  physical deadline enforcement is claimed.
- **Ownership.** Over every work-entity parameter of every action of the final module: creation
  only by enqueue; removal by nobody; `attempts` only by claim; `owner`, `lease_until` and
  `available_at` only by the capabilities the contract lists, through their subject; payload
  immutable (`UNAUTHORIZED_WORK_*`). A capability cannot bind its own work entity
  (`WORK_ITEM_BINDING`) or write it in an authored effect (`AUTHORED_WORK_EFFECT`).
- **Genesis and provenance.** A genesis may hold items that satisfy `ValidWork` (Core checks it,
  `GENESIS_INVALID` otherwise). Validity is not provenance: an imported LEASED item is trusted
  state with no recorded claim, and its deadline is not assumed live.
- **Migrations.** Core enforces only target validity. The host contract: attempts never decrease
  or are reused; terminal stays terminal; no migration manufactures or reactivates a lease
  (READY → LEASED is prohibited); a LEASED item keeps its lease or becomes READY with unchanged
  attempts (then attempts < M); claim generations and time semantics are never reinterpreted.
  The suite's negative controls show both breaks with real Core migrations.
- **Not guaranteed.** Single physical execution, exactly-once external effects, that an
  expired worker stops, fairness or ordering. Composition with RequestFlow is asynchronous: a
  transition emits a command and an adapter enqueues in a separate commit.

```python
q = WorkQueue("document_work", worker=Worker, time=Time, max_attempts=3,
              payload={"document": Id[Document]})
q.enqueue(authorized=lambda *, actor, **_: is_admin(actor), context={"actor": Id[User]})
q.claim(eligible=lambda w, *, worker, **_: is_active(worker))
q.complete(state={"doc": Document}, effects=[lambda w, *, doc, **_: set_(doc.processed, True)])
q.renew(); q.retry(); q.fail()
q.recover(authorized=...); q.exhaust(authorized=...); q.cancel(authorized=...)
```

Callables receive the subject positionally (enqueue has none) and every other parameter by
keyword, only those they declare. The reference application and its conformance suite are in
`models/examples/work_queue/` (`python -m models.examples.work_queue.run`;
`scripts/conformance.sh 507 [quick|full|complete]`, report `target/conformance/507-report.json`
with an evidence record per verification obligation).

## Purchase approval conformance (feature 506)

[`examples/purchase_approval/`](examples/purchase_approval/) composes all three model kinds into
one workflow: a RequestFlow `purchase_request` (with its embedded StateMachine), a standalone
StateMachine `budget`, and an Approval over the flow's request entity whose eligibility is a
query over `User`. It runs the whole lifecycle on the pinned Core Release:
author → lower → admit → evaluate → commit → replay → verify.

```sh
python -m models.examples.purchase_approval.run   # the lifecycle, step by step, exit 0 if it matches
scripts/conformance.sh 506                            # the suite; writes target/conformance/506-report.json
BEHAVIOR_FULL_PROPERTIES=1 scripts/conformance.sh 506 # full mode: the integration gate CI runs
scripts/conformance.sh 506 complete                   # full conformance: every check must pass
```

Static verification of the reference module (C19) passes since Core 0.15.0 (feature 508):
verifier 0.10.0 proves both uniqueness postconditions of the **unchanged** Approval module
(BehaviorHash `sha256:a04ba37…531779`), which verifier 0.9.0 left inconclusive
(behavior-ir-core#35). The readiness registry is empty, and full conformance is complete. A
future Core limitation is reported as `blocked` only through an explicit readiness entry.

Every expected outcome is stated by hand in `expected.json`
(specs/506-e2e-conformance/contracts/reference-workflow.md), never copied from a run. Each
check reports one status:
- passed or failed;
- inconclusive, unverifiable, unsupported or blocked, each with its owning layer.

Only `passed` counts as passed.

**What the suite demonstrates**:
- construction, admission and identity;
- decisions and refusals at their boundaries;
- the Store's commit contract under contention, stale observations and re-creation;
- data replay, behavior replay, integrity negative controls and commit-history consistency;
- static verification of the reference module;
- authoring agreement between the Python binding and the Rust model authority;
- execution agreement between the Python engine interface and the released Core CLI.

**What it does not demonstrate**:
- Core's own correctness, because both execution paths run the same engine;
- properties outside the verifier's modeled fragment and assumptions;
- backends other than the in-memory one and the Python reference backend;
- command execution.
