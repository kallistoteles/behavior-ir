# Draft Core issue — global rules disable validated-state promotion

For review only. Proposed layer: Core Store validation. Priority: performance investigation.
Baseline and commands: [README](README.md). Minimal code: [public Backend probe](store-probe/src/main.rs).

## Property and observed failure mode

For a valid exact parent and a successful ordinary transition, reuse validity only when the
new state and all required observable outcomes are equivalent to the full-reference path.
The present investigation demonstrates unnecessary full-state enumeration for a constant global
rule; it does not establish a universal constant-time algorithm for arbitrary global predicates.

The probe uses an ordinary `Target(value: Int)`, an action assigning `value = 1`, and an optional
closed invariant. It changes one configuration dimension: no global invariant, literal `True`,
or `count(select(Target)) >= 0`. No Safety Models, generated actions or private application code.

Each Store starts with N seeded entities. Three update/commit rounds are observed, with an extra
evaluation at the exact same head before each commit. A separate fixed-N history control warms
32 commits before the observations. Three creation controls then increase the live set by one.

| Global rule | N | Members enumerated after each observed new head | Same-head repeat |
| --- | ---: | ---: | ---: |
| none | 1 / 16 / 128 / 512 | 0 | 0 |
| literal `True` | 1 / 16 / 128 / 512 | N | 0 |
| count query | 1 / 16 / 128 / 512 | N | 0 |

The first evaluation immediately after genesis enumerates zero members: Core already established
that initial state's validity. For N=16, both global cases enumerate 17, 18 and 19 members after
the successive creations. The local module enumerates zero. With N fixed at 16 and 32 prior commits,
the global cases still enumerate 16 and the local case zero. This isolates the enumeration count;
it does not prove total cost is independent of history length or backend implementation.

## Ranked hypotheses and controls

1. **Whole-module eligibility blocks cache promotion.** Predicts identical N-member rescans for
   literal `True` and the query rule, but not the local module. Supported by measured counts.
2. **Actual global query evaluation alone causes the growth.** Predicts the literal rule avoids
   the growth. Rejected as the sole explanation by the literal-rule control.
3. **History length alone causes the enumeration.** Predicts increasing history at fixed N changes
   the number of members returned. Not observed in the fixed-N control; other history-related
   costs are not excluded.

## Source correspondence and scope

In Core 0.15.0, `dependency::local_module()` requires `global_invariants().is_empty()`.
`validate_incremental_child()` returns `None` for an ineligible module; `carry_incremental_child()`
does not advance the cached validity identity in that case. At the next head,
`validate_snapshot()` misses the exact-identity cache and calls `validate_snapshot_full()`.
That function enumerates each entity type's live keys and reads their values before checking the
complete snapshot. These production paths explain the neutral probe's counts.

This is not a missing incremental-validation implementation. Core feature 015 already supplies
a conservative optimization and explicitly allows full-reference fallback for globals/queries.
The proposed work extends its justified coverage rather than replacing the validity contract.

## Requirements for further work

- Establish observational equivalence with full validation under explicit Backend assumptions,
  including admission/validity, rejection and error order, changesets, commands and canonical
  history/replay-relevant results. Invariant preservation alone is insufficient.
- Bind reusable validity to the exact parent/history, module, schema and validation profile;
  unsupported dependencies, invalid anchors and uncertain cache ownership must fail closed.
- Account for all potentially affected invariants, references, queries, creations, removals and
  simultaneous effects. A smaller visited set needs a justified frame/dependency argument.
- Separate affected dependency size, live population, history length and backend/query costs.
  Do not promise O(1) work for arbitrary global predicates or silently stop validating entities.
- Preserve the original full validator as reference/fallback and test invalid-state/error controls,
  module switches, migrations, concurrent commits and recovery before accepting a remediation.

No safe production workaround eliminating these scans was established. Removing a genuine global
invariant changes the domain contract and is not a proposed fix. The exact private application's
dominant cost and long-duration recovery behavior remain unmeasured.
