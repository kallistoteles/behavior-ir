## 1. Optional uniqueness: verified semantics and exact public syntax

`unique(q, by=key)` means that distinct members cannot have equal keys. There is no implicit exclusion for an absent optional value. This follows directly from the pinned implementation: the ordinary fold inserts each key's encoded JSON into a set and returns false on a duplicate; `Value::None` encodes as JSON null. Consequently, two selected members whose projected optional keys are both absent collide. This is a source-derived semantic conclusion, not an observed test outcome. Sources: [Core unique evaluation](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-core/src/eval.rs#L943-L951), [optional decoding](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-core/src/semantic/value.rs#L69-L72), [null encoding](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-core/src/semantic/value.rs#L99-L116), and [binding unique API](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/python/behavior/query.py#L219-L221).

Recommended documentation wording:

> `unique` compares every selected key, including absent optional values. Two selected `None` keys collide. To require uniqueness only for present values, filter with `.where(lambda row: row.key.is_some())` before applying `unique`.

The following uses the public DSL exactly; it is source-checked and **unexecuted**:

```python
from behavior import BehaviorModule, Option, entity, field, invariant, select, unique

@entity
class Item:
    key = field(Option[str])

@invariant
def present_keys_unique():
    present = select(Item).where(lambda row: row.key.is_some())
    return unique(present, by=lambda row: row.key)

model = BehaviorModule(entities=[Item], invariants=[present_keys_unique])
```

The public APIs are `Query.where`, `Expr.is_some`, and `unique(..., by=...)`; `is_some` is an expression method, not a separately exported free function. Sources: [where](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/python/behavior/query.py#L41-L44), [is_some](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/python/behavior/expr.py#L174-L181), [exports](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/python/behavior/__init__.py#L15-L40), [module construction](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/python/behavior/module.py#L169-L188), and [Core query API example](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/specs/007-relational-queries/contracts/query-api.md#L27-L34).

Minimal future reproduction: two distinct Item identities with absent keys; then two with the same present string. Expected model semantics: unfiltered uniqueness rejects both duplicate-key states; filtered uniqueness permits the two absent keys and rejects the duplicated present string. **Actual runtime and verifier results: not collected.**

## 2. Approved-module enforcement and the host boundary

Application `Approval` records decisions and derives outcomes. It contributes ordinary actions and predicates; it neither changes the subject's lifecycle itself nor supplies Core commit authority. The contract explicitly has no Approval-specific authorization and scopes its global laws to ordinary states reachable from a valid base state. Sources: [Approval runtime contract](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/specs/503-approval-model/contracts/approval-contract.md#L29-L44), [guarantees and base-state assumption](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/specs/503-approval-model/contracts/approval-contract.md#L104-L120).

Core trusted governance is a separate commit boundary. Required Store-v2 governance authenticates authorization under trusted keys and an exact policy. Authorization binds the exact candidate, Store and parent, behavior/schema, evidence policy, execution policy, proof/waiver content, and independently supplied context. The host must supply `AuthorizationContextV2` independently to `commit_with_context`; copying signed evidence's context is not a host observation. Sources: [pinned governance contract](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/docs/governance.md#L3-L17), [public commit entry point](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-store/src/store.rs#L82-L90), [independent authorization comparison](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-verify/src/governance/trusted.rs#L819-L864).

Existing allowlists must be named accurately. `EvidencePolicyV2` lists trusted authorities and **execution policy identities**; `ExecutionPolicyV2` lists accepted verification profiles, verifier versions and solvers, required checks, waiver policy, time/context requirements and trusted issuer intervals. Those are real enforcement mechanisms. Neither policy body defines a Store-wide set of approved BehaviorHashes. Both bodies deny unknown fields. A behavior hash in the exact authorized subject prevents substitution of that authorization onto another behavior; it does not itself establish a universal Store admission allowlist. Sources: [evidence policy body](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-verify/src/governance/trusted.rs#L1243-L1269), [execution policy eligibility check](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-verify/src/governance/trusted.rs#L895-L912), [execution policy body](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-verify/src/governance/trusted.rs#L1340-L1355), [matching behavior subject](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-verify/src/governance/trusted.rs#L914-L932). Store evidence enforcement reads the immutable genesis policy and requires independent context when authorization is required; `require:none` may commit without attached evidence. Source: [Store evidence boundary](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-store/src/store.rs#L3472-L3526).

Recommended exact wording:

> `Approval` is application behavior. Trusted commit authorization is a separate Core governance mechanism that authenticates an exact transition under the Store's evidence policy. Its behavior binding prevents evidence substitution; the published policy schema does not define a Store-wide approved-BehaviorHash set. A host requiring approved-module activation must enforce its deployment policy across every writer, migration and activation boundary, with independent context and coordinated access to the Store/backend.

For Safety deployment, the existing public reference host checks the incoming exact BehaviorHash and policy-set hash, validates the incoming state at a full HistoryRef, and coordinates activation, invocation and migration through one lock. Its docstring explicitly requires exclusive Store/backend access and an equivalent transactional/distributed boundary for multiple processes. This is a host protocol, not a newly proposed Core feature or an assurance that a Python lock controls other handles. Sources: [deployment reference](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/models/examples/safety_models/deployment.py#L1-L72), [published explanation](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/models/README.md#L541-L550).

## 3. Current limits and carefully bounded research candidates

### Relational invariants and composite uniqueness

Queries are candidate-local. Nested queries, other-entity existence/reference reads and query-bearing entity rules are prohibited; global queries belong in module invariants or action conditions. Grouped universal rules are explicitly out of scope for the query feature. Source: [Core query specification clarifications](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/specs/007-relational-queries/spec.md#L82-L99), [enforced query placement](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-core/src/admit/typecheck.rs#L915-L929), [candidate lambda disables queries](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-core/src/admit/typecheck.rs#L1151-L1174).

`unique` accepts one expression; the published Core type enum has no tuple/product value constructor for a composite key. The Approval specification explicitly documents the scalar-key/no-tuples limit and explains its own action-local child checks plus structural ownership proof. This is not evidence that all relational invariants are impossible: scalar global uniqueness and aggregate invariants already exist. Sources: [Core value types](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-core/src/semantic/types.rs#L122-L138), [Approval rationale](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/specs/503-approval-model/spec.md#L155-L163), [public scalar uniqueness example](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/specs/007-relational-queries/contracts/query-api.md#L27-L34).

Minimal domain-neutral candidate properties, with no suggested encoding asserted as already supported:

| Candidate | Intended property and useful controls | Evidence / missing outcome |
| --- | --- | --- |
| Cross-entity relational invariant | Every nonterminal Child points to a Parent whose phase is permitted. Include a terminal-child control and a prohibited-parent transition. | General arbitrary joins are outside candidate-local queries. Existing restricted `LifecycleDependency` handles a defined subset, with explicit supported effects/guards. [Published subset](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/models/README.md#L474-L507). No minimal arbitrary-relation admission/proof outcome collected. |
| Composite uniqueness | Distinct Row identities may share `left` or `right`, but not the pair `(left, right)`. Controls: same-left/different-right, different-left/same-right, and duplicate pair. | No tuple key in current value types. A scalar concatenation is not an established injective encoding. No candidate wire IR, admission diagnostic or runtime result collected. Research needs an explicit desired API and encoding before an expected-versus-actual report is possible. |

### Mutual entity references: separate declarations, existence and reciprocal equality

The Python `Id` and `Ref` factories accept a string entity name, supporting declarations such as `field(Ref["Right"])` before Right's class exists. Core resolves Id/Ref targets against declared entity names and hashes target names, rather than recursively hashing the target entity definition. The cycle checker inspected here concerns **derived-value dependencies**, not a claim that all entity reference cycles are invalid. Sources: [binding factories](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/python/behavior/types.py#L210-L231), [Core target resolution](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-core/src/admit/resolve.rs#L112-L125), [Id/reference hashing](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-core/src/admit/hash.rs#L75-L86), [Ref field hashing](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-core/src/admit/hash.rs#L145-L152), [derived graph scope](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-core/src/admit/graph.rs#L1-L4).

`Ref` establishes target existence; it does not by itself state reciprocal equality. A minimal research case can distinguish (a) Left and Right declarations pointing to each other, (b) atomic fresh creation of both with valid target IDs, (c) one missing target, and (d) the stronger property `Right[Left.right].left == Left.id`. Intended lifecycle semantics check existence in the complete resulting state, including creations; the stronger reciprocal rule requires its own stated relational semantics. Source: [lifecycle specification](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/specs/006-entity-lifecycle/spec.md#L257-L267), [Ref meaning](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/specs/006-entity-lifecycle/spec.md#L328-L331). **Actual admission, runtime and verifier outcomes for these mutual-reference cases: not collected.** No mutual-reference bug is established.

### Same-type surviving binding plus creation: exact encoder restriction

The pinned verifier gathers surviving State-bound children and created children, then rejects a same-type pair when that entity type has an invariant or constraint. The exact internal error is `EncodeError::Unsupported("canonical same-type child identity order for T")`. The source explains that decoded same-type identity ordering is not modeled by SMT string equality where child obligations could change the observable first-failure prefix. This is narrower than claiming that every action binding and creating the same type fails. It also covers other ways of producing multiple same-type children. Source: [encoder guard](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-verify/src/encode.rs#L1688-L1716).

Source-checked public DSL scaffold, **unexecuted**:

```python
from behavior import (
    BehaviorModule, Id, Input, action, constraint, create, entity, field,
)

@entity
class Item:
    value = field(int)

@constraint
def nonnegative(item: Item):
    return item.value >= 0

@action
def copy_item(existing: Item, *, new_id: Input[Id[Item]]):
    create(Item, id=new_id, value=existing.value)

model = BehaviorModule(
    entities=[Item], constraints=[nonnegative], actions=[copy_item],
)
```

The constraint decorator, create syntax, parameter roles and module keyword lists follow the [published lifecycle example](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/skills/behavior-authoring/examples/actions_and_lifecycle.py#L25-L59). The new identity must be fresh, independently of this verifier restriction; [runtime freshness enforcement](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/crates/behavior-core/src/eval.rs#L3230-L3244) rejects an already-used identity.

Candidate property: copying a valid existing Item into a fresh identity preserves `value >= 0`. Source analysis predicts the internal encoder guard applies because the existing Item survives and another constrained Item is created. **Actual public attestation/report and runtime outcome: not collected.** Collect those separately before calling this a reproduced precision limitation. Controls: creation with no same-type State parameter; same-type binding/create without entity rules; removal of the old binding with fresh creation. No control outcome is claimed.

### Equivalent guards: a concrete documentation discrepancy

The release's [verification Skill table](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/skills/behavior-verification/SKILL.md#L232-L254) still says only `not_(any_(...))` matches uniqueness and recommends rewriting `count(select(T).where(...)) == 0`. That blanket recommendation is inconsistent with the pinned Core documentation's verifier-0.10 **supported typed parent-count relation**: `not any(Q,p)` and `count(where(Q,p)) == 0` impose coherent conditions for supported total predicates. Source: [Core parent-count congruence](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/docs/verification.md#L269-L308).

The refinement is deliberately structural. It preserves query structure and operand order; only literal true filters may be omitted. Its documented fragment includes typed primitive reads/literals, compatible comparisons, Boolean combinations, option tests and literal membership. Checked arithmetic, derived calls, unwraps, nested aggregates and unrecognized forms receive no new relation. Other aggregates retain their existing rules. This does **not** establish arbitrary semantic equivalence or that every uniqueness property using either guard is PROVEN. Source: [exact fragment and exclusions](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/docs/verification.md#L277-L308).

Recommended replacement wording:

> Verifier 0.10.0 relates `not_(any_(Q, p))` and `count(Q.where(p)) == 0` for its documented supported total typed predicate fragment. Equivalent expressions outside the recognized structural fragment may still need separate investigation. Report a minimized module and its actual pinned verification result before classifying a remaining form-sensitive case as current precision debt.

Minimal future comparison: one Item type with scalar key, module-level scalar uniqueness, fresh creation, and either `not_(any_(select(Item), lambda row: row.key == key))` or `count(select(Item).where(lambda row: row.key == key)) == 0`; the negative control omits the guard. Keep entity rules absent to avoid the unrelated same-type child-order restriction. Then vary one expression form at a time. **Actual reports: not collected; no difference between those two simple guards is asserted.** Keep remaining arithmetic/derived/reordered cases as minimized, unreproduced research.

Safety `LifecycleDependency` also has its own recognized guard contract. Its published documentation explicitly says semantically equivalent unrecognized guards remain Unsupported. This is a separate structural checker boundary, and does not establish a Core verifier bug. Source: [Safety guard contract](https://github.com/kallistoteles/behavior-ir/blob/21ba441299998ca0c6baf53a5178d1b591216b1f/models/README.md#L488-L507).

### Documented conservative verifier limits

The pinned verifier documentation still lists changed captures, fresh extrema after member removal/change, and partial-sum range reasoning as relational precision limits. Whole-state migration properties can also be inconclusive. Unknown-member witness slots are for concretely confirming counterexamples; lack of a bounded witness is never a proof. Sources: [symbolic summaries and witnesses](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/docs/verification.md#L89-L115), [known limitations](https://github.com/kallistoteles/behavior-ir-core/blob/6b93898a9375113f7a8946f23ab5535319b6f5d6/docs/verification.md#L184-L196). A real overflow counterexample must not be relabeled precision debt just because it involves a sum.

This note authorizes no implementation work. Any later upstream report needs the exact pinned module, intended property, admission result, named profile, actual verification outcome and runtime confirmation when a counterexample is claimed. No such new reproduction artifacts were produced here.
